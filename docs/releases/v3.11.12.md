# v3.11.12 — 容量守卫固定开销动态化（实测代替常量，根治漏拦盲区）

## 背景

v3.11.11 的容量守卫用常量 `TOOL_SCHEMA_RESERVE_TOKENS=24K` 补固定开销（system/memory/skills/工具 schema）——
用户指出这是"缓解非根治"：实测固定开销约 7.4 万里，仍有约 4.9 万未被覆盖。
盲区只是从"估 95% 实 100%+"挪到"估 95%+24k"，没封住；且常量过时（注释锚点还是"82 工具 15k"）。

审查确认 Eta 已有自测能力：每轮成功请求的 `input_tokens` 已持久化（`conversation_messages.input_tokens`）
且在 UI 状态可用（`AgentMessageUi.usage.inputTokens`）。可直接反推真实固定开销：

```
实测固定开销 ≈ 上一轮 input_tokens − rawEstimate(该轮历史)
             = system + memory 核心 + skills 索引 + 工具 schema（随工具/记忆开关自动变化）
```

## 修复

### 策略调参（改阈值/预留方式，不称根因）

1. **守卫固定开销改为「实测优先 + 常量下限 + 冷启动回退」**（`AgentAppState.sendCurrentMessage` R2 分支）：
   - `measuredOverhead = (lastInputTokens − rawEstimate(homeState.history)).coerceAtLeast(0)`
   - `guardOverhead = measuredOverhead ?: TOOL_SCHEMA_RESERVE_TOKENS`（无上一轮→冷启动→回退 24K 下限，不退化）
   - 守卫判定：`rawEstimate(editHistoryPrefix) + guardOverhead >= window` → 阻止发送并提示压缩/新建
   - 实测值随工具数/记忆量/开关自动跟随，不再用过时常量；`coerceAtLeast(0)` 防负值反放大。

### 触发条件
仅当编辑重发前缀非空、且有上一轮成功请求时走实测；否则维持 v3.11.11 的下限行为。

## 验证

- 编译 + 受影响测试全绿（`AgentConversationRevisionReducerTest`）。
- 逻辑为纯计算（读取已有 input_tokens），容错由 `coerceAtLeast(0)` + 冷启动 fallback 保证。
- 全量回归：新增非环境失败 = 0。

## 升级后使用建议

- **旧会话可继续用**：追加新消息对话完全正常；但「编辑重发」依赖历史消息带 messageId，
  旧会话多数历史无此字段，R1 ID 定位会退化到旧的条数差值逻辑（不崩，巨型长会话下仍可能截偏）。
  此时容量守卫（动态固定开销）兜底，不会再直接 CONTEXT_OVERFLOW，但会比新会话少一层精确。
- **建议**：巨型长会话（几千条）常编辑重发 → 新开会话，享受完整 R1；正常/中等会话可直接继续。
- **小技巧**：旧会话先发一条新消息（带 messageId），之后编辑该条即可按 ID 定位，但仅对该条之后的编辑生效。

> 按 INVARIANTS Changelog 规范，本改动归「策略调参」（改预留方式/阈值），写清触发条件；
> 不改变守卫"必须挡真近窗口请求"的语义，仍 raw 保守口径无误拦（真实提升是堵住 4.9 万漏拦盲区，
> 让守卫在固定开销 >24K 的真实场景下也能正确拦截）。
