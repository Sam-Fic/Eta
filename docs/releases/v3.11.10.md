# v3.11.10 — 编辑重发 CONTEXT_OVERFLOW 根治（boundary ID 定位 + 发送前容量守卫）

## 背景

真机反馈（2026-10-11，3.11.6）：长会话（5050 条）中**编辑用户消息并重发**报
「Runtime 运行失败 · 模型上下文超过容量限制」，而界面显示用量仅 20%~50%（模型容量 1M）。

报告证据链完整：5 次自动压缩把上下文降到 ≈202K（20%），随后编辑重发 run 失败；
服务商返回 `CONTEXT_OVERFLOW`（`context_length_exceeded`）属实——**请求确实超出容量**，
但并非"上下文真的太大"，而是**编辑重发的截断点算偏，把完整历史（journal 505 万字符）带出**。

根因（代码验证）：

1. **`AgentConversationRevisionReducer.boundary()` 用「UI/journal 用户消息条数差值」反推截断点**
   （`retainedUserOrdinal = historyUserIndices.size - (userMessageIndices.size - targetUserOrdinal)`）。
   巨型会话下 UI 与 journal 条数不等 → 差值法失效 → 截断点算偏。
2. **编辑分支 journal 兜底**（`homeState.copy(journal = editBoundary?.journalPrefix ?: homeState.journal)`）：
   截断为空时回退到未截断全量 journal，方向相反。
3. **无发送前容量保护**：本地估算使用默认校准（新 run 首轮无 usage → 0.25 保守低估），
   不触发既有硬裁剪，直接发出 → 被服务商拒绝。

## 修复

### 逻辑修复

1. **R1 boundary 改 ID 定位**（`AgentConversationRevisionReducer`）：优先按 `messageId`
   在 journal 中匹配截断点（新消息进入 journal 时已带 `_eta_message_id`）；旧数据无 ID
   → 退化到原差值逻辑（不抛异常）。消除"条数对位"假设，巨型会话不再算偏。
2. **R2 发送前容量守卫**（`AgentAppState.sendCurrentMessage` 编辑分支）：编辑重发携带前缀历史时，
   用**未乘校准的 raw 口径**预估 token，≥ contextWindow 则**阻止发送**并提示
   「建议压缩历史或新建会话」，避免被服务商 CONTEXT_OVERFLOW 拒绝。
3. **R3 journal 兜底修正**（`AgentAppState` 编辑分支）：截断 prefix 为空时**不回退全量 journal**。

### 体验

4. **R4 CONTEXT_OVERFLOW 文案**（`AgentModelFailure` http/stream 两处）：追加
   「建议先手动压缩历史，或新建会话继续当前任务」——用户不再面对裸错误。

## 验证

- 新增 2 个 @Test：
  `boundaryUsesMessageIdOverCountWhenUiAndJournalDiffer`（T-R1：journal 比 UI 多一轮 user 时，
  ID 定位到正确截断点，不含多余早期历史）、
  `boundaryDegradesToCountWhenJournalHasNoMessageIds`（T-R1b：旧数据无 ID → 退化差值不崩）。
- 受影响测试类全绿：`AgentConversationRevisionReducerTest`。
- 全量回归：新增非环境失败 = 0。

> 系统性判断：缺陷非 fork 压缩引入——是上游「计数定位」固有缺陷被长会话放大（压缩让会话能越跑越长，

> R2 守卫也会在发出前阻止并给出可操作提示。
